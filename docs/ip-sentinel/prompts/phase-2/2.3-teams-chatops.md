# 2.3 — Teams ChatOps

*Prepend [`00-shared-preamble.md`](../00-shared-preamble.md).*

**Goal:** reach the same Assistant from Microsoft Teams.

**Deliverables**
- Teams bot/app entry (reuse the 1.6 Graph integration) routing to the 2.1 agent.
- Map the Teams user → platform identity, tenant, role, tier; enforce Pro gating.
- Same audit/redaction/cost path as the SPA.

**Acceptance**
- [x] A Pro user asks a question in Teams and gets the correct tenant-scoped answer; a Basic user is told it's a Pro feature.
- [x] Identity/tenant resolution is correct; no cross-tenant access.

## Implementation notes
- **Transport decision**: Teams offers several ways to receive messages (Azure Bot Service/Bot
  Framework, Graph change notifications, Outgoing Webhooks). This chunk uses a Teams **Outgoing
  Webhook** per tenant - Island Pacific hands each customer one URL,
  `POST /api/v1/integrations/teams/chatops/{tenantId}`, to paste into their Teams connector when they
  set it up. That keeps tenant scope explicit in the URL (never inferred from anything in the request
  body) and makes the request/response model synchronous, which matches `AssistantAgentService.answer`'s
  existing single-call contract - no Bot Framework SDK or Graph subscription/RSC lifecycle needed.
- **Reuse of 1.6**: `TeamsChannelConfig` (same `integration_config` row, kind `"teams"`) gets one new
  optional field, `chatOpsHmacSecret` - Teams' shared secret for that tenant's Outgoing Webhook
  connector. It's optional so tenants using only 1.6's outbound card notifications are unaffected;
  ChatOps is live for a tenant only once this field is set. The existing `TeamsAuthTokenProvider`
  (app-only AAD token) and `TeamsGraphClient` (now with a new `getUserPrincipalName` method,
  `GET /users/{aadObjectId}`) are reused as-is to turn the sender's Teams-verified Azure AD object id
  into their `User.email` - the exact "reuse the 1.6 Graph integration" the chunk asked for.
- **Request authentication**: `TeamsWebhookSignatureVerifier` (new, stateless utility) validates
  `Authorization: HMAC <sig>` against `base64(HMACSHA256(rawBody, base64Decode(secret)))` - Microsoft's
  documented Outgoing Webhook contract. The raw body is read directly off `HttpServletRequest.getInputStream()`
  rather than via `@RequestBody`, so the exact bytes are HMAC-verified before any JSON parsing occurs.
- **Identity -> tenant -> role -> tier chain** (`TeamsChatOpsController`, new): tenant comes only from
  the URL path; the sender's AAD object id (Bot Framework `ChannelAccount.aadObjectId`, present on
  every Teams channel message) resolves via Graph to a UPN, then `UserRepository.findByEmail` and
  `UserTenantRoleRepository.findByTenantIdAndUserId(tenantId, userId)` - **only a role row for this
  exact tenant** lets the request proceed. A signature-valid request from a real, provisioned user who
  simply isn't provisioned on *this* tenant gets a polite "you don't have access to IP Sentinel for
  this organization" reply, never the assistant - this is the isolation guarantee, since nothing about
  the AAD identity alone implies IP Sentinel tenant access. Pro/Basic gating reuses the existing
  `EntitlementService.getEntitlementTier` (no new gating logic); a Basic tenant gets "The AI Assistant
  is a Pro-tier feature...". `TenantContextHolder` is bound with the real resolved `TenantContext`
  (not a synthetic one) for the duration of the agent call, in a try/finally, so 0.7's governance
  decorator (redaction/audit/cost-metering) applies identically to the SPA and streaming paths.
- `SecurityConfig` permits `/api/v1/integrations/teams/chatops/*` (Teams cannot present an IP Sentinel
  bearer token); the endpoint authenticates itself via the HMAC check above instead.
- **Verification**: new unit tests - `TeamsWebhookSignatureVerifierTest`, `TeamsChannelConfigTest`
  (new optional-field cases), `TeamsGraphClientTest` (new `getUserPrincipalName` cases), and
  `TeamsChatOpsControllerTest` (Pro answered, Basic upsell message, bad/missing signature, unconfigured
  tenant/ChatOps, unregistered user, user-provisioned-on-a-different-tenant, blank question, and
  `TenantContextHolder` always cleared including when the agent throws) - all green, and the full
  default `mvn test` is green (285 tests, no regressions). A new Postgres-backed
  `TeamsChatOpsIsolationIntegrationTest` (real repositories: two tenants, one real AAD identity
  provisioned on tenant A only, proves tenant B's ChatOps URL denies that same person) was added
  alongside the other Docker/Spring-context integration tests and excluded from the default build in
  `pom.xml` the same way. It could not be run to a live green result in this session's shell for the
  same pre-existing reason `2.1`'s and `1.8`'s notes recorded (`QueryFanoutExecutor`'s `HttpClient`
  construction hits `java.io.IOException: Unable to establish loopback connection` merely booting the
  full `ApplicationContext`, unrelated to this chunk's code - reproduced identically here). Confirm with:
  `mvn test -Pdocker-integration-tests -Dtest=TeamsChatOpsIsolationIntegrationTest`.
- Not built (out of scope per the chunk's own deliverables): a Teams app manifest/setup UI for
  admins to paste the webhook URL and secret into `integration_config` - that's a config-authoring
  concern, not the routing/gating this chunk covers, and no such UI exists yet for 1.6's fields either.
