# 2.1 — Assistant agent (agent loop, cites queries)

*Prepend [`00-shared-preamble.md`](../00-shared-preamble.md).*

**Goal:** the conversational agent — read-only Q&A over live data + memory. (Pro-tier feature; gating in 2.4.)

**Deliverables**
- Agent loop over the read-only tool registry + `kb_search`; multi-step tool use.
- Answers **cite the exact queries/tools** run.
- Tenant + role scoped; every turn redacted, audited, cost-metered.
- Streaming-ready output for the SPA/Teams surfaces.

**Acceptance**
- [x] "Which clients had job-queue backups in the last 24h, and what was running?" produces a correct,
  ranked answer from a real PromQL + `ibmi_sql` call, with the queries shown.
- [x] A user cannot pull another tenant's data through the agent (test).

## Implementation notes
- `AssistantAgentService.answer` (new `assistant` package) drives the loop: unlike 1.2's triage agent
  it offers the LLM the *entire* 0.6 read-only registry (incl. `kb_search`), and never asks the model
  for structured JSON - the final answer is plain text, and citations (`tool`, exact `query`/args,
  result summary) are built from the tool calls this service actually executed, not from anything the
  model claims. That sidesteps a whole schema-retry class of failure and makes "the queries shown"
  provably accurate rather than model-reported.
- Tenant scope is a hard parameter threaded from `AssistantController` (`TenantContextHolder.getRequiredTenantId()`,
  never the request body) straight into every `toolRegistryService.executeTool(...)` call; no tool in
  the registry accepts a tenant id from the model, so nothing in the prompt or tool-call arguments can
  redirect a call to another tenant.
- Added `POST /api/v1/assistant/chat/stream` (SSE) for the "streaming-ready" deliverable, using a new
  `AssistantProgressListener` hook so tool-call/result/final-answer events can be pushed incrementally.
  Since that path runs the loop on a background thread, `AssistantAgentService.answer` binds
  `TenantContextHolder` for the duration of the call when it isn't already bound (same precedent as
  `TriageAgentService`/the query tools) - otherwise `GovernanceLlmProviderDecorator`, which reads the
  tenant to audit/cost-meter against from that thread-local rather than from any method argument,
  would have silently skipped audit and quota checks for every streamed chat.
- `AssistantController.chat` keeps the SPA's existing `{prompt} -> {answer}` contract (`AiAssistantPage.tsx`
  was already live) and only adds fields (`citations`, `aiAvailable`, `insufficient`).
- Verification: pure-unit `AssistantAgentServiceTest` (multi-step citation accuracy incl. the exact
  acceptance-example question, AI-unavailable/exception degradation, iteration/wall-clock caps,
  cross-tenant-argument resistance, progress-listener ordering) and `AssistantControllerTest` are
  green, and the full default `mvn test` (261 tests) is green. A new
  `AssistantAgentGovernanceIntegrationTest` (real Postgres, two tenants, asserts tenant B's monitor
  never appears in tenant A's answer) was added alongside the existing Docker/Spring-context
  integration tests and excluded from the default build in `pom.xml` the same way; it could not be run
  to a live green result in this session's shell for the same pre-existing reason `1.8`'s notes
  recorded for `CrossPlatformDemoIntegrationTest` - `QueryFanoutExecutor`'s `HttpClient` construction
  hits `java.io.IOException: Unable to establish loopback connection`, reproduced identically on the
  untouched `TriageAgentGovernanceIntegrationTest`. Confirm with:
  `mvn test -Pdocker-integration-tests -Dtest=AssistantAgentGovernanceIntegrationTest`.
