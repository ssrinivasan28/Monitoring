# 1.6 — Microsoft Teams integration (first)  ⭐

*Prepend [`00-shared-preamble.md`](../00-shared-preamble.md).*

## Context
The **first** external integration — lowest friction (Graph/Azure AD already used by the monitors).
Covers staff + customer delivery and is the on-ramp for Teams ChatOps (2.3).

## Scope
**In:** posting incidents to Teams channels, per-tenant config, dedupe + status updates.
**Out:** conversational ChatOps (2.3), other channels (1.7 / later).

## Dependencies
- 1.3 (incidents), `integration_config` (0.1). Reuse the monitors' OAuth2/Graph token pattern
  (`OAuth2TokenProvider`).

## Deliverables

### 1. Config
- Per-tenant Teams settings in `integration_config` (kind=`teams`): tenant/team/channel + credentials
  (via DPAPI). Enable/disable per tenant.

### 2. Posting
- On a new incident, post an **Adaptive Card**: severity, title, affected systems, AND the root cause +
  evidence **when present** (omit gracefully when the LLM was off).
- **Dedupe:** one card per incident (store the message ref); **update** the card on status change
  (ack/assigned/resolved).
- Manual "Push to Teams" from the console (1.4) uses the same path.

### 3. Reliability
- Idempotent send (no duplicate cards on retry); backoff on Graph throttling; failures surfaced, not swallowed.

## Constraints / gotchas
- **Tenant isolation:** a card only ever goes to its own tenant's channel — assert this.
- Secrets via `CredentialProtector`; never log tokens.

## Testing
- New incident ⇒ exactly one card to the correct tenant channel (mock Graph); status change ⇒ card updated.
- Retry ⇒ no duplicate card.
- No-narrative incident ⇒ card still valid (root-cause section omitted).
- Cross-tenant: a tenant's incident never posts to another's channel.

## Acceptance
- [x] One card per incident to the right tenant channel, updated on status change.
- [x] Idempotent; secrets via DPAPI; isolation enforced.

## References
- `OAuth2TokenProvider` (existing Graph token pattern). Extends to ChatOps in 2.3.
