# 1.10 — Agent-directed workflow actions

*Prepend [`00-shared-preamble.md`](../00-shared-preamble.md).*

**Goal:** let the agent *decide* which external-system action(s) an incident warrants — page,
ticket, chat-post, or none — instead of a fixed rule always firing every channel. Writes stay
scoped to integration systems (ServiceNow/Jira, PagerDuty/Opsgenie, Teams/Slack) — **never** to
IBM i or Windows.

**Deliverables**
- Extend the Notification Router (1.6/1.7) with an **action-recommendation step**: given the
  triage output (severity, confidence, similar-incident history), the agent proposes which
  channel(s) to use and drafts the content (ticket summary, page reason, chat message).
- **Human-in-the-loop by default**: the recommended action is queued for one-click approve/edit/
  reject in the Incident Console before it fires. A per-tenant config flag may allow
  auto-send for a specific channel + minimum-confidence combination (off by default).
- Every fired action is idempotent, audited (`agent_runs`/`tool_calls`), and attributed to the
  agent run that proposed it.

**Constraints / gotchas**
- No new write surfaces beyond the existing 1.6/1.7 integration adapters — this chunk adds
  *decision-making* on top of them, not new external integrations.
- Auto-send config must default off; changing it is an admin (0.3 RBAC) action, itself audited.
- Reuse 1.7's idempotent delivery — an approved recommendation must not double-fire.

**Acceptance**
- [ ] A seeded high-severity incident produces a queued, editable action recommendation with a
      drafted message, correctly attributing the proposing agent run.
- [ ] Approving it fires exactly once via the existing adapter; rejecting it fires nothing.
- [ ] Auto-send stays off by default; enabling it is an audited RBAC-gated admin action.
