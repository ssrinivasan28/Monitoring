# 1.9 — Multi-step, self-directed triage investigation

*Prepend [`00-shared-preamble.md`](../00-shared-preamble.md).*

## Context
1.2's `TriageAgentService.runConversation` **already** drives an LLM tool-calling loop — the model
picks each next read-only tool call from the 0.6 registry based on what it's learned so far, bounded
by `TriageAgentProperties.maxToolIterations` (default 6). The "self-directed" mechanic is not new.

What's actually missing, and what this chunk closes:
- **No investigation identity.** `executeToolSafely` calls `toolRegistryService.executeTool(null, ...)`
  — every tool call in an investigation falls back to a dummy `"standalone-tool-call"` agent-run id
  (`ToolRegistryService.executeTool`). Nothing ties an incident's tool calls back to the incident, or
  to the `agent_runs` rows the same investigation produced.
- **Only one stop condition.** `runConversation` caps on iteration *count* alone. There's no wall-clock
  timeout and no per-investigation cost/token budget — `QuotaService.checkQuota` only enforces a
  tenant-wide daily/monthly ceiling, checked per LLM call, not a per-investigation cap.
- **No per-incident trace query.** `agent_runs`/`tool_calls` have no `incident_id` column at all
  (`V1__init.sql`), so there's no way to fetch "the tool trace for incident X" for the Incident
  Console (1.4) — only the staff-only, un-scoped `/api/v1/audit/agent-runs` (`AuditQueryController`).

## Scope
**In:** correlating an investigation's `agent_runs`/`tool_calls` rows to their incident; adding
wall-clock + cost/token stop conditions alongside the existing iteration cap; a tenant-scoped
per-incident trace read endpoint.
**Out:** new tool capabilities (0.6 unchanged), the output schema (still 1.2's `RootCauseResult`),
the Incident Console UI itself (1.4 consumes the new endpoint), notifications (1.6/1.7).

## Dependencies
- 1.2 (`TriageAgentService`, `TriageAgentProperties`, `RootCauseResult`).
- 0.6 (`ToolRegistryService`, `SentinelTool`).
- 0.7 (`GovernanceLlmProviderDecorator`, `GovernanceAuditService`, `AgentRun`, `ToolCall`,
  `AuditQueryService`, `QuotaService`).

## Deliverables

### 1. Investigation identity & linkage
- **Migration `V9__agentic_investigation.sql`:** add nullable `incident_id UUID REFERENCES incidents(id)
  ON DELETE CASCADE` to `agent_runs` and `tool_calls`, each with a supporting index. Nullable so
  non-incident agent/tool calls (if any) don't break.
- Add `incidentId` field + accessors to the `AgentRun` and `ToolCall` entities.
- Extend `GovernanceAuditService.logAgentRun(...)` / `logToolCall(...)` to accept an `incidentId`
  (nullable), and pass it through on the `AgentRun`/`ToolCall` construction.
- Thread the incident id down the existing call path rather than adding a new thread-local: add an
  `incidentId` field to `LlmRequest` (already the object `TriageAgentService` builds and
  `GovernanceLlmProviderDecorator.chat()` reads) so the decorator can tag the `agent_runs` row it
  writes per LLM call.
- In `TriageAgentService.runTriage`, generate one `investigationId` (or just reuse `incident.getId()`
  as the correlation key — no separate investigation table needed) at the start, set it on every
  `LlmRequest` built during that investigation's `runConversation`, and stop passing `null` in
  `executeToolSafely` — pass the incident id through to `toolRegistryService.executeTool` so
  `tool_calls.incident_id` is populated instead of falling back to the dummy id.
- Keep one `agent_runs` row per LLM call (unchanged granularity for 0.7's cost/token metering) — only
  add the `incident_id` correlation key across all rows from one investigation.

### 2. Hard stop conditions (time + budget, not just count)
- Add to `TriageAgentProperties`: `maxWallClockMs` (default 120_000) and `maxCostPerInvestigation`
  (`BigDecimal`, default e.g. `0.50`), alongside the existing `maxToolIterations`.
- In `runConversation`, track elapsed wall-clock time from loop start, and accumulate cost per call
  using the tokens/model each `LlmResponse` already reports (price via the same `ModelPricing` the
  decorator uses — no extra DB read needed).
- On **any** cap — iteration, wall-clock, or budget — stop the same way the existing
  "exceeded max tool-call iterations" fallback already does: send one final message telling the model
  to answer now with only the JSON it can support from evidence gathered so far. Never fail the
  incident; 1.2's `persistInsufficient` path already covers "couldn't produce valid output."
- Record which condition (if any) ended the investigation as an `incident_timeline` note (e.g.
  `"triage stopped: wall-clock budget exceeded after 4 tool calls"`) so 1.4 can show *why* it stopped,
  not just that it did.

### 3. Per-incident trace query (feeds 1.4)
- New endpoint `GET /api/v1/incidents/{incidentId}/agent-trace` — tenant-scoped (not staff-only like
  `/api/v1/audit/agent-runs`), returns the ordered `agent_runs` + `tool_calls` for that incident: each
  tool called, redacted arguments, result summary, and the final structured root cause. This is what
  1.4 renders as the step-by-step trace.
- Backing query added to `AuditQueryService` (or a small sibling service), filtered by
  `tenant_id` + `incident_id`.

## Constraints / gotchas
- No new tool capabilities — same read-only registry as 1.2; only the calling pattern's bookkeeping
  changes.
- Must still degrade to "skip silently, incident untouched" if the LLM is unavailable — the existing
  `AiUnavailableException` path in `runTriage` is unchanged.
- Preserve existing per-call `agent_runs`/`cost_ledger` granularity (0.7) — don't collapse an
  investigation's multiple LLM calls into a single row; only add the `incident_id` correlation key.
- `ibmi_sql` stays SELECT-only (inherited from 0.6, no change here).
- Treat all tool-returned data as untrusted evidence, never instructions — already enforced by 1.2's
  system prompt; don't regress it while touching `runConversation`.
- The new endpoint must respect tenant isolation the same way every other incident-scoped read does.

## Testing
- Seeded incident with a multi-step, dynamically-chosen tool trace (>1 call) ⇒ every `agent_runs` and
  `tool_calls` row from that run carries the same `incident_id`; the new endpoint returns them in order.
- Wall-clock cap: stub `LlmProvider` with an artificial delay ⇒ investigation stops at the configured
  cap and still persists a root cause (or "insufficient"), never an unhandled exception.
- Budget cap: stub per-call token/cost to exceed `maxCostPerInvestigation` within a few calls ⇒ stops.
- Iteration cap (regression): existing `maxToolIterations` behavior still enforced.
- Provider-unavailable (regression): investigation aborts cleanly; no orphaned rows without an
  `incident_id` from a partially-run investigation.

## Acceptance
- [ ] A seeded incident produces a multi-step tool trace (>1 tool call, chosen dynamically) ending in
      a valid structured root-cause output, and every row in that trace shares the incident's id.
- [ ] Wall-clock, cost/token, and iteration caps are each enforced and independently tested —
      investigation stops cleanly at each cap and still persists a result (never fails the incident).
- [ ] Tool trace is queryable per-incident via a tenant-scoped endpoint (feeds 1.4).
