# 1.7 — ITSM two-way sync (ServiceNow/Jira)

*Prepend [`00-shared-preamble.md`](../00-shared-preamble.md).*

**Goal:** keep ServiceNow/Jira as system-of-record with lightweight two-way status sync.

**Deliverables**
- Create/enrich a ticket from an incident (with AI context when present).
- **Two-way status sync** using the 1.5 state mapping (in-app ack/assign/resolve ↔ ITSM state).
- **Idempotent** delivery (no duplicate tickets); retry with dead-letter; per-tenant config.
- Adapter abstraction so ServiceNow and Jira share an interface.

**Acceptance**
- [x] An incident creates exactly one ticket; resolving in-app resolves the ticket and vice-versa (test with a mock ITSM).
- [x] Retries don't duplicate; tenant isolation intact.

## Implementation notes
- `ItsmAdapter` interface (`ServiceNowAdapter`, `JiraAdapter`) mirrors 1.6 Teams' poll-and-sync design:
  a scheduled sweep and the manual "Push to ITSM" console action share one `ItsmSyncService.syncIncident`
  path. `itsm_tickets` gives idempotent, one-row-per-incident ticket tracking (same dedupe-on-race
  pattern as Teams' `teams_notifications`); `itsm_sync_failures` adds retry-with-dead-letter, which
  Teams didn't need.
- The referenced "1.5 state mapping" was never built (1.5 shipped no assign/resolve endpoints or
  mapping class). This chunk adds the minimal missing piece - an in-app `/resolve` endpoint - plus
  `ItsmStateMapper`, so the acceptance test's "resolving in-app" case has something to call. 1.5's
  broader lifecycle (assign endpoint, notes/comments, transition audit trail) is still open.
