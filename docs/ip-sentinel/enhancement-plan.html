01 · Executive summary

From alerts to answers

The current suite is excellent at detection: each monitor polls a system, checks a static threshold, and emails when it trips. What it can't do is reason — correlate a burst of alerts into one incident, explain the likely cause, or remember how the last one was fixed. Today that work is done by an engineer with Grafana in one window and a green-screen in another.

IP Sentinel keeps every existing monitor as-is — they become the sensor layer — and adds a central AI operations analyst on top. When something breaks, it assembles a complete incident: what happened, everything related to it across platforms, the most likely root cause, the matching runbook, and what a human should check next. You can also just ask it questions in plain English. Every capability is read-only — it advises, it never acts.

02 · The problem today

What the current suite can't do

Five gaps that slow every investigation down.

  • Noise
    Alert storms, no correlation. One IBM i outage trips subsystem, job-queue, QSYSOPR, and dependent Windows-service monitors at once — arriving as many disconnected emails with no single "incident" view.
  • Blind spots
    No cross-client / cross-platform picture. Each box is an island with its own Grafana; nobody sees the whole fleet at once.
  • Manual
    Every diagnosis starts from scratch. An engineer reads charts, logs, and IBM i state by hand to guess the cause, each time.
  • False alarms
    Static thresholds only. Fixed limits fire on harmless spikes and miss slow-building problems entirely.
  • No memory
    Knowledge lives in people's heads. The same incident is re-investigated repeatedly; runbooks and past fixes aren't searchable.

04 · Why this matters

The business case

Where the time and risk actually go today, and what closing each gap is worth.

  • Faster MTTR
    Minutes, not hours, to root cause. One correlated incident with evidence and a matched runbook replaces reading Grafana + logs + green-screen by hand for every outage.
  • Fewer false pages
    Less alert fatigue for on-call. Dedupe, flap detection and correlation turn 4+ disconnected emails from one outage into a single actionable incident.
  • Outages avoided
    Problems caught before they trip a threshold. Forecasts on disk/ASP fill, cert expiry and job-duration drift give days of warning, not a page after the fact.
  • Engineer leverage
    One engineer covers more clients. A single fleet view and ChatOps Q&A replace per-box Grafana logins and manual cross-referencing.
  • Compounding value
    Every resolved incident makes the next one faster. Runbooks and past fixes become searchable memory instead of leaving with the engineer who solved it.
◆
What doesn't change.

Zero changes to the 21 production monitors, zero writes to IBM i or Windows, and email alerting keeps working as a fallback throughout. This is additive investment, not a rip-and-replace.

09 · Under the hood

How the AI analyst works

One pluggable LLM abstraction (ClaudeApiProvider or a local model, with routing & fallback). Every call is redacted, audited, and metered.

Triage loop, per incident

  • Detect & correlate
    Group simultaneous breaches across monitors, platforms & tenants.
  • Gather context
    Pull the metrics, logs & IBM i state around the event via tools.
  • Retrieve memory
    Fetch the matching runbook & most-similar past incidents (pgvector).
  • Reason
    LLM produces root cause, evidence, severity & suggested checks.
  • Notify
    One enriched incident to console + configured channels. No actions taken.

11 · Increasing agent autonomy

How the agents get more capable, without more risk

Three planned upgrades to the agent roster above — still entirely read-only.

  • Self-directed investigation
    Today's Triage Agent runs a fixed gather-then-reason sequence. The upgrade lets it choose its own next tool call — check subsystem, then decide whether to pull job history or QSYSOPR next — stopping once it has enough evidence or hits a cost/time budget.
  • Proactive, self-triggered investigations
    Anomaly and Forecasting agents already run on a schedule. The upgrade lets them kick off a deeper investigation themselves when something crosses a risk threshold — surfacing a ready-made Insight before any monitor even breaches.
  • Agent-recommended actions
    Instead of a fixed rule always paging every channel, the agent recommends which action(s) an incident warrants and drafts the message — a human approves, edits or rejects with one click before anything is sent.
▲
The line that doesn't move.

All three stay inside the existing read-only tool registry and the human-approves-every-action model. Auto-remediation — restarting a service, editing a threshold, writing to IBM i or Windows — remains explicitly out of scope: a bad automated fix is a worse outage than a missed alert.

12 · In practice

Three scenarios

SCN-1

IBM i subsystem outage — the correlation win

QINTER stops. Within seconds the subsystem, job-queue-count, and QSYSOPR monitors breach, and a dependent Windows sync service goes down. IP Sentinel correlates all four into one incident, surfaces the QSYSOPR message that names the cause, retrieves the "QINTER restart" runbook and two similar past incidents, scores it Critical, pages on-call and opens a ServiceNow ticket.

→ one actionable incident instead of 4+ disconnected emails

SCN-2

Slow-building capacity risk — predictive

ASP usage trends upward over two weeks. No static threshold has fired, but the forecast projects 95% in six days. IP Sentinel raises a proactive Insight with the projected date and growth driver.

→ warned six days early, before any outage

SCN-3

Plain-English investigation — ChatOps

An engineer asks in Teams: "Which clients had job-queue backups over the last 24h, and what was running?" The agent runs PromQL across tenants plus an IBM i SQL lookup and replies with a ranked list and the top jobs — citing the queries it ran.

→ an answer in seconds, fully traceable

Phased delivery

Governance and the UI shell are foundational — built first, not bolted on.

  • Phase 0

    Foundation + governance + UI shell

    MVP

    Central data plane (remove Grafana); Postgres schema + pgvector; Spring Boot query gateway, LLM abstraction, tool registry, agent loop; governance day one (audit, PII redaction, Azure AD SSO + RBAC, cost metering); React shell with dashboards at parity for the two pilot monitors.

  • Phase 1

    Correlation & triage + integrations

    MVP slice

    Correlation engine producing RAG-grounded incidents in the console; ServiceNow/Jira, PagerDuty/Opsgenie, Teams/Slack, SIEM/webhook. Existing per-monitor email retained as fallback.

  • Phase 2

    Natural-language ChatOps

    Conversational interface in the SPA (WebSocket streaming) and in Teams/Slack, running the agent over the read-only tools + RAG, scoped by role.

  • Phase 3

    Adaptive thresholds & learning

    Baselines, forecasts and anomaly detection surfaced in Insights, plus threshold recommendations; learn from analyst feedback stored in Postgres to reduce noise over time. Includes the self-triggered investigation upgrade (section 10).

  • Phase 4

    Production hardening

    DR/backup, platform self-monitoring, secrets rotation, resilience & performance/security testing, AI-safety eval/red-team, SOC 2 & accessibility. Required before general production rollout.

15 · Risks & mitigations

What could go wrong, and what already guards against it

Named up front so they're managed, not discovered mid-build.

  • Wrong answer
    The AI's root-cause hypothesis is wrong or overconfident. Mitigated by: every claim must cite the evidence it came from (§09), confidence score shown, human approves every action, degrades cleanly to "insufficient data" rather than guessing.
  • Data exposure
    Sensitive log/config data reaches an external LLM. Mitigated by: PII/secret redaction before every call (governance spine, §16), a local-model option for data that can't leave the network, and a read-only tool registry with no credential passthrough.
  • Cost overrun
    LLM usage cost grows unpredictably with fleet size. Mitigated by: per-tenant quotas, cost/token dashboards, and Claude↔local routing so expensive calls can shift to a cheaper model as volume grows.
  • Prompt injection
    A crafted log line or config value tries to instruct the agent. Mitigated by: all tool-returned data is treated as untrusted evidence, never as instructions — enforced in every agent's system prompt and covered in Phase 4's AI-safety red-team.
  • Low adoption
    Engineers keep using Grafana/email out of habit. Mitigated by: email alerting is kept as a fallback throughout the rollout, dashboards reach parity before Grafana is dropped, and the MVP proves value on one pilot tenant before wider rollout.

Read-only by design.

No remediation, no auto-restart, no auto threshold edits, no writes to IBM i or Windows. The AI observes, correlates, explains, and recommends — a human takes every action. Closed-loop remediation (a natural future phase via the existing ServiceScheduler) is deliberately deferred.

Appendix · Glossary

Plain-English terms

For readers who don't need the acronyms to be strangers.

AIOps

"AI for IT Operations" — using AI to correlate, explain and predict infrastructure issues instead of only alerting on them.

LLM

Large Language Model — the AI (Claude, or a local model) that reads evidence and writes the root-cause explanation.

RAG

Retrieval-Augmented Generation — the AI looks up your actual runbooks and past incidents before answering, instead of relying only on general knowledge.

pgvector

A PostgreSQL extension that lets the database search runbooks/incidents by meaning, not just keyword match — what makes RAG possible.

Tenant isolation

Guarantee that one client's data, dashboards and AI answers can never be seen by another client, even though they share the same platform.

Model routing / fallback

The system can send a request to Claude or to a local/on-prem model, and automatically fall back to the other if one is unavailable — never a hard dependency on one provider.
